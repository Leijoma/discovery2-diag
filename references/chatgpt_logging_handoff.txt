3. Valeo BCU — new and important structural information

The second half of faultread-20260809-4.log switched to BCU.

This produced the most useful new information from the final session.

BCU SecurityAccess

On the first BCU connection attempt, the log contains:

27 01
→
67 01 EB CD

So the BCU returned seed:

EB CD

reference tool then sent:

27 02 C0 10

and the BCU answered:

7F 27 83

i.e. a negative response to SecurityAccess. The operator then noted loss/failure of communication.

So we have strong confirmation of the usual sequence:

27 01
→ 67 01 <seed>

27 02 <key>
→ success or negative response

For this capture:

seed = EB CD
attempted key = C0 10
result = negative response 7F 27 83

Do not infer the seed→key algorithm from this one sample.

BCU restart / second SecurityAccess attempt

After restart, reference tool again sends:

27 01

and then:

27 02 4A 8A

After this attempt the diagnostic session continues and WriteLocalIdentifier traffic begins.

The response to the seed/key exchange is not cleanly separated in this part of the passive log, so do not mark:

4A 8A

as a universally valid key.

What is supported is:

BCU diagnostic write/output mode appears to use SecurityAccess before WriteLocalIdentifier commands.

Confidence: high.

4. BCU output/control banks

Once the BCU session is active, the same four WriteLocalIdentifier commands appear repeatedly:

3B 22 00 00 00 00
3B 23 00 00 00 00
3B C1 00 00 00 00
3B C2 00 00 00 00

The length-prefixed raw frames are:

06 3B 22 00 00 00 00 63
06 3B 23 00 00 00 00 64
06 3B C1 00 00 00 00 02
06 3B C2 00 00 00 00 03

Their checksums are consistent with the normal additive KWP framing:

06 + 3B + 22 = 63
06 + 3B + 23 = 64
06 + 3B + C1 = 102 → 02
06 + 3B + C2 = 103 → 03

Thus these are valid BCU:

WriteLocalIdentifier (SID 0x3B)

operations.

They appear repeatedly around output attempts such as front/rear fog lights, daylight running lights and indicators.

They also appear around window commands.

5. Candidate BCU output-bank model

The strongest structural hypothesis is:

LID 22 → 32-bit diagnostic/output state bank
LID 23 → 32-bit diagnostic/output state bank
LID C1 → 32-bit diagnostic/output state bank
LID C2 → 32-bit diagnostic/output state bank

with wire format:

3B <LID> <b0> <b1> <b2> <b3>

Example:

3B 22 00 00 00 00

would mean writing a four-byte state to bank 22.

Confidence
SID 3B = WriteLocalIdentifier       CONFIRMED
LIDs 22/23/C1/C2 exist              CONFIRMED
Each carries four payload bytes     CONFIRMED
They occur in BCU output context    HIGH
They are output/control bitfields   STRONG HYPOTHESIS
Individual bit mappings             UNKNOWN
6. Critical warning: all captured BCU bank payloads are ZERO

Every observed write in this final session uses:

00 00 00 00

for all four banks.

Therefore it is not valid to map:

front fog light = LID 22 bit X
window up       = LID C1 bit Y
etc.

from this capture.

The nearest annotation is not sufficient evidence.

7. Likely interpretation of the zero writes

The best current hypothesis is that these are reset / diagnostic override clear / inactive-state writes, not the actual activation state.

Supporting observation:

During front left window up, reference tool writes the four zero banks:

22
23
C1
C2

and then later writes the same four zero banks again before the next annotated command.

That pattern is consistent with something like:

clear all diagnostic output overrides

or:

return all output banks to inactive state

rather than an output-specific command.

Confidence: medium/high structural hypothesis.

Do not implement it as fact yet.

8. Why the actual BCU “ON” writes may be missing

Possible explanations supported by the capture structure, but not proven:

A. reference tool sent a short activation pulse between logged frames and it was missed.
B. The UI operation was inactive/not accepted, analogous to the SLABS tests.
C. The four zero-bank writes are preparation/reset, while another command controls activation.
D. reference tool normally writes one non-zero bank followed quickly by zero, but the non-zero frame was lost by the passive logger/framing.

No choice between these can be made from the final capture.

Claude should therefore preserve:

22/23/C1/C2

as candidate bank IDs, but should not create individual output decoders.

Bottom line

Den sista reference tool-sessionen löste inte SLABS-lamptesterna, men gav två ganska värdefulla resultat:

EAT-kommandona för Read/Clear Faults är nu reproducerade och kan betraktas som bekräftade, trots reference tools eget felmeddelande.

Och ännu viktigare för BCU: vi har nu starkt stöd för att dess diagnostic-outputmekanism använder SecurityAccess + 3B WriteLocalIdentifier mot fyra fyrbytesbanker 22, 23, C1, C2. Själva bitmappningen återstår, eftersom den enda state vi fångade var 00000000.

Det är den del jag skulle be Claude lägga in i protokollbiblioteket som structural/high-confidence, men uttryckligen inte som färdiga output-decoders.
